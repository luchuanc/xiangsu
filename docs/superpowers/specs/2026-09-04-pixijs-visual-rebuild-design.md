# PixiJS 移动 H5 RPG 视觉重建设计

日期：2026-09-04  
状态：已确认  
已选方案：A——保留领域系统，重建真实 PixiJS 游戏表现层

## 1. 问题与目标

当前工程已经具备存档、地图数据、移动判定、回合制战斗、装备、技能、词条、Combo、招募、奖励和深渊回响等领域能力，但浏览器中的可见产品仍是工程占位：场景类主要生成只读 ViewModel，未把地图、角色、NPC、怪物、战场与 HUD 转换成 Pixi 显示对象；`GameFlowController` 又把测试入口渲染成页面底部的 DOM 按钮。因此玩家看到的是暗色空画布和调试控件，而不是游戏。

本轮重建的目标不是继续补领域功能，而是把现有规则装配成真正可玩的移动 H5 像素 RPG。第一里程碑必须完整跑通：

> 标题页 → 城镇自由移动 → 靠近并交互 NPC → 选择第一层 → 野外移动 → 触碰怪物 → 回合制战斗 → 领取奖励 → 回城

只有上述流程在真实浏览器里可见、可触控、可辨识，才算第一里程碑完成。随后再把已有背包、队伍、技能、Combo、商店、深渊回响和十层内容全部接入同一视觉系统。

## 2. 产品与视觉方向

### 2.1 视觉 thesis

“篝火照亮的暗黑远征”：16-bit 像素风，城镇使用暖木、石墙与火光，野外逐层转为冷蓝、腐绿和深渊紫；金色只表达稀有成长与可操作焦点，猩红只表达危险、Boss 和致命反馈。

### 2.2 内容计划

1. 标题页：全画布世界氛围图、游戏名、开始/继续两个明确入口。
2. 城镇：可走地图、主角、功能 NPC、建筑招牌、NPC 近身提示和功能面板。
3. 野外：多层瓦片地图、可见怪物、宝箱、出口、层数和队伍状态。
4. 战斗：我方左侧、敌方右侧、顶部速度顺序、底部五类指令、伤害与 Combo 反馈。
5. 成长管理：背包装备、四人编队、技能铭石、Combo 来源、商店与设置。
6. 终局：第 6～10 层深渊氛围、强力 Boss、回响目标和高品质奖励演出。

### 2.3 交互 thesis

- 探索的手感来自“跟脚”：虚拟摇杆按下即移动，角色步行动画、脚步声和相机跟随同步，碰撞时不滑步。
- 战斗的爽感来自“蓄力—命中—结果”：出手顺序先提示，攻击位移与命中闪白紧凑，伤害数字、破盾、击倒和 Combo 横幅按领域事件依次出现。
- 获得关键装备时必须有明显的“构筑跃迁”反馈：稀有卡停留、关键数值前后对比、Combo 拼合点亮；演出可跳过但信息不可丢失。

## 3. 设计坐标与移动端约束

- 继续使用冻结设计坐标 `640 × 360`，横屏 `contain` 居中。
- 568×320 是最低验收视口；844×390 用于常见全面屏验收。
- 所有地图瓦片、角色、图标和文字位置落在整数逻辑像素；纹理使用 nearest 采样，不开抗锯齿与 mipmap。
- 所有主要触控区域换算到 CSS 后至少 44×44，主要按钮间距至少 8 CSS px。
- 安全区只改变 HUD 锚点，不缩放世界地图；超宽区域扩展背景或留暗边。
- 竖屏、视口过小、页面 hidden 和 WebGL context lost 继续沿用现有系统门禁；这些状态恢复后必须重建可见场景而非只恢复逻辑状态。

## 4. 架构

### 4.1 保留的权威层

以下现有能力继续作为唯一真源，不在表现层复制公式或另造状态：

- `GameStore`、`SaveCoordinator`、`GameSaveV1`：权威存档和原子提交。
- `MovementSystem`、`CollisionGrid`、`EncounterAi`、`CameraSystem`：移动、碰撞、怪物与相机。
- `BattleCommandGateway`、`ActionResolver`、`BattleReducer`：战斗指令、事件和快照。
- 装备、技能、词条、Combo、招募、掉落和奖励服务：构筑与成长。
- `ContentCatalog` 和资源清单：所有明确 ID、数值和资源引用。

表现层只能读取这些结果并发出命令，不得自行结算伤害、扣物品、改变存档或猜测内容字段。

### 4.2 新增场景显示根

新增 `PixiSceneRoot`，它是可被 `SceneRouter` 整体挂载/卸载的 `Container`，内部固定包含：

1. `mapBack`：地面瓦片与地图背景。
2. `actors`：角色、NPC、怪物、宝箱；按脚底 Y 排序。
3. `mapFront`：屋檐、树冠、墙体前景遮挡。
4. `worldFx`：交互圈、命中特效、飘字。
5. `hud`：当前场景 HUD。
6. `screen`：全屏管理页和奖励页。
7. `modal`：对话、确认、目标选择和错误提示。
8. `transition`：淡入淡出与遭遇转场。

全局 `PixiRootLayers` 仍承载系统级旋屏、错误、toast 与 WebGL 恢复；业务场景的可见对象全部随 `PixiSceneRoot` 生命周期销毁，避免旧场景残留。

### 4.3 渲染适配器边界

领域 ViewModel 保留为可测试的数据投影，新建小型 Pixi 适配器消费它们：

- `TileMapRenderer`：把地图 tile layer 和前景层转换为批量 Sprite。
- `FieldActorRenderer`：把 `ActorView`/运行时位置转换为 `AnimatedSprite`，处理四向 idle/walk、锚点和 Y 排序。
- `FieldHudRenderer`：队伍血条、层数、右上入口、动态摇杆、交互按钮。
- `DialogueRenderer` / `TownPanelRenderer`：NPC 对话和功能面板。
- `BattleStageRenderer`：队伍/敌人站位、选中、状态、Boss 条和速度时间轴。
- `BattleHudRenderer`：普攻、技能、防御、道具、更多、目标选择和日志抽屉。
- `BattleEventPresenter`：严格按已保存的领域事件顺序播放动作、伤害、治疗、护盾、倒地和 Combo 表现，不重新结算。
- `ManagementScreenRenderer`：把现有 Inventory/Party/Skill/Combo screen adapter 的 state、preview 和 commit 操作转换为游戏内全屏界面。

每个适配器只负责三件事：创建显示对象、根据快照更新显示、销毁自身资源引用。它们不持有存档真源。

### 4.4 DOM 的新职责

`#game-flow-ui` 不再显示底部调试按钮。DOM 只保留：

- 旋屏、视口过小、致命错误等系统覆盖层。
- 与 Pixi 控件位置同步的透明语义按钮，用于屏幕阅读器、键盘和稳定的自动化定位；视觉由 Pixi 绘制。
- 文本输入等 Canvas 不适合承载的原生能力，目前首版没有此类输入。

语义按钮不得形成可见按钮条，也不得成为业务状态的第二真源。

## 5. 场景设计

### 5.1 标题页

- 640×360 全画布像素背景，远处城镇灯火和深渊入口形成视觉目标。
- 游戏名是第一层级；继续存档存在时“继续”是主按钮，“新游戏”是次按钮。
- 新游戏覆盖仍使用现有二次确认规则。
- 首次用户手势同时解锁 Web Audio；失败只显示静音状态，不阻断进入游戏。

### 5.2 城镇

- 使用现有 `town` MapDefinition、碰撞网格和相机系统，给 `TownScene` 增加与野外共用的 field runtime，而不是使用固定 NPC 按钮列表。
- 主角在保存的城镇位置生成，可用左下动态摇杆移动；相机跟随但限制在地图边界。
- NPC 以 24×32 四向像素角色显示，头顶显示短名称；主角进入 40 像素半径后显示交互标记，点击右下按钮打开现有 NPC 功能。
- 酒馆、铁匠、技能导师、商人、旅店、制图师、深渊观测者均通过地图对象 ID 进入，不保留一排直达调试按钮。
- NPC 面板关闭后恢复原坐标、朝向和摇杆输入。

### 5.3 野外探索

- `ExplorationScene` 继续每 fixed-step 消费一份 `InputSnapshot`，但更新后同步真实地图、角色和怪物 Sprite。
- 玩家移动时播放 walk，停止时回 idle；方向来自本帧位移，不从按键字符串猜测。
- 怪物使用 EncounterDefinition 明确的 fieldSpriteId。触碰后立即锁输入，播放短促遭遇转场，再进入战斗。
- 宝箱、出口和交互对象有世界内图形，不靠文字按钮；不可用时交互按钮灰化并显示原因。
- HUD 左上为当前四人队伍生命简条，右上为地图/背包/队伍/设置，左下摇杆，右下交互/菜单。

### 5.4 回合制战斗

- 我方最多四人位于左侧前后排，敌方最多六人位于右侧；Boss 使用更大 64×64 规格。
- 顶部时间轴严格按当前速度/既有顺序投影，不自行预测规则外行动。
- 一级指令固定为普攻、技能、防御、道具、更多；“更多”只含撤退和日志。
- 选择单体技能时合法目标高亮，不合法目标压暗；全体/自身技能走明确确认态。
- `BattleEventPresenter` 消费提交成功后返回的事件：动作前摇 → 命中/治疗/护盾 → 数字 → 状态 → Combo → 终局。重试不得重播未提交结果，也不得重新掷 RNG。
- 首个可玩切片至少实现 idle、attack、hit、down 和通用技能特效；完整技能专属动画后续按现有 AnimationDefinition 扩充。

### 5.5 奖励与管理页

- 奖励页优先展示金币/经验，再按品质逐张揭示装备或铭石。
- 关键掉落显示当前装备对比、关键输出/生存变化和新增/失去 Combo；领取仍走现有原子保存。
- 背包、队伍、技能、Combo 与设置使用游戏内全屏页，复用现有 screen adapter 的 preview/confirm/失败重试语义。
- 移动端布局遵循 640×360：列表与详情按固定区域切换，不用浏览器长页面滚动堆卡片。

## 6. 美术资源策略

### 6.1 ImageGen 用途

使用 ImageGen 生成项目原创像素资源，首批只覆盖第一里程碑需要的完整视觉集合：

- 标题背景与 logo 参考稿。
- 城镇 tileset、第一层野外 tileset。
- 主角探索四向 sprite；首批功能 NPC 与第一层遭遇怪探索 sprite。
- 初始三名角色与第一层敌人/Boss 战斗 sprite。
- UI 皮肤参考、按钮/面板/血条/状态/Combo 图标参考。
- 通用斩击、法术、命中、治疗、护盾与 Combo 爆发特效。

ImageGen 输出先作为原创母稿，再按冻结规格切分、去除半透明脏边、补齐帧、统一色板和锚点。不得直接把带有生成文字、假 UI 框或不规则帧尺寸的整图投入运行时。

### 6.2 规格

- 地图瓦片：16×16。
- 探索单位：每帧 24×32，脚底锚点 (12,28)。
- 普通战斗单位：每帧 48×48，锚点 (24,42)。
- Boss：每帧 64×64，锚点 (32,58)。
- 色板：城镇暖灰/赭石/烛火橙；第一层苔绿/石青；深渊紫只作为后五层专属。
- 字体：像素 BitmapFont；小字号必须在 568×320 下清晰，不用 CSS 平滑字体覆盖核心 HUD。

首批生成后必须做一张 640×360 城镇组合截图与一张战斗组合截图，先验证风格统一，再批量生成其余楼层，避免十层资源同时返工。

## 7. 数据流与失败处理

### 7.1 探索

触摸/键盘 → `InputLayer` → fixed-step → `MovementSystem`/`EncounterAi` → 场景状态 → renderer 更新 Sprite/相机 → 接触或交互命令 → 应用服务原子保存 → SceneRouter 转场。

保存失败时保持当前地图和坐标，恢复输入并显示游戏内错误提示；不得提前移除怪物或切入下一场景。

### 7.2 战斗

Pixi 指令控件 → `BattleCommandGateway` → 校验/解析/RNG/事件 → `SaveCoordinator` 成功 → Store 快照与事件 → `BattleEventPresenter` → 下一指令或终局。

提交中锁定所有指令；失败后保持原快照、原目标选择和可解释错误，可重试；成功事件播放期间不允许重复提交。

### 7.3 管理与奖励

Pixi 控件修改 screen draft → preview → confirm → CAS 保存 → 成功后刷新权威 snapshot。失败保留 draft、选中项和预览，明确显示重试入口。

## 8. 实施分解

整个重建按单写入任务串行推进，避免在同一 Pixi 场景骨架上并发冲突。

### VIS-001：真实 Pixi 场景骨架

- 建立 `PixiSceneRoot`、场景 renderer 生命周期和纹理解析适配器。
- 让 TitleScene 能在画布上显示最小可见内容。
- 隐藏现有 DOM 调试按钮条，保留系统覆盖与语义镜像。

### VIS-002：第一里程碑美术包

- 用 ImageGen 生成并整理标题、城镇、第一层、首批角色/NPC/怪物、战斗与核心 UI 资源。
- 更新 manifest/atlas 并通过尺寸、帧名、引用和 nearest 校验。

### VIS-003：标题与可走城镇

- 完成标题交互、城镇 tilemap、主角、NPC、摇杆、相机和 NPC 面板。
- 真实走到制图师处进入第一层。

### VIS-004：第一层探索

- 完成野外 tilemap、怪物、宝箱、出口、探索 HUD 与触碰转战斗。

### VIS-005：可见战斗与奖励

- 完成双方站位、时间轴、五类指令、目标选择、基础事件演出、Combo 横幅、胜负和奖励回城。

### VIS-006：完整管理 UI

- 接入背包/装备/重铸、队伍/招募、技能/铭石、Combo、商店、旅店、设置和诊断页。

### VIS-007：十层与深渊视觉扩展

- 扩展 2～10 层 tileset/环境色、怪物/Boss sprite、深渊回响和关键掉落演出。
- 完成平衡回归、全流程浏览器验证和移动真机抽查。

## 9. 测试与验收

### 9.1 自动测试

- renderer 单测：纹理 ID、帧切换、锚点、整数坐标、前后景分层、销毁。
- 场景集成测试：prepare/enter/pause/resume/exit、输入锁、相机同步、失败重试。
- 战斗表现测试：事件只消费一次、sequence 顺序、跳过、Combo 链与终局。
- 资源测试：manifest、atlas frame、sheet 尺寸、动画 clip、资源引用。
- 保留现有领域全量单测、typecheck、lint、build、content/assets 校验。

### 9.2 真实浏览器验收

第一里程碑必须提供真实 Playwright 运行证据，不能用 `test.skip` 或注入存档替代主线：

1. 568×320 和 844×390 均能看到完整标题画面与按钮。
2. 开始新游戏后，城镇地图、主角和 NPC 可见。
3. 触屏摇杆能移动主角，动画、碰撞和相机同步。
4. 玩家必须在地图内靠近 NPC 才能打开功能面板。
5. 第一层野外地图和怪物可见，触碰怪物进入战斗。
6. 战斗中双方单位、生命、速度顺序和指令 UI 可见，普攻能推进回合。
7. 胜利后奖励可领取并返回城镇。
8. 页面无可见调试按钮条，无 console error、pageerror、未处理 Promise。
9. 关键画面保存截图：标题、城镇、野外、战斗、奖励各一张。

### 9.3 完成定义

- “逻辑测试通过但画布为空”不算完成。
- “能通过隐藏 DOM testid 操作但看不到对应 Pixi 控件”不算完成。
- “只有静态地图，主角不能持续触控移动”不算完成。
- 第一里程碑达成后，用户能不看调试说明自行完成一次从城镇出发、战斗、领奖、回城的循环，才进入完整十层扩展。

## 10. 明确非目标

- 不重写已验证的领域公式、内容表、存档 schema 和 Combo/战斗结算内核。
- 不为了首版做 WebGPU、复杂 shader、大规模粒子或过早性能优化。
- 不在第一里程碑同时生成十层全部最终美术；先验证统一风格与真实玩法闭环。
- 不用 CSS/DOM 模拟地图、角色或战斗单位。
- 不保留“工程占位”作为任何正常游戏状态的最终可见内容。
